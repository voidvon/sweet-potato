# 轻量营销视频插件接入规划

> 状态：规划中  
> 更新日期：2026-08-28  
> 涉及项目：`agent-tool`、`remotion-video`

## 1. 背景与结论

不在 `remotion-video` 中重复建设用户管理、权限、API Key、素材库和 AI 能力。轻量营销视频作为 `agent-tool` 的一个业务插件接入，复用主项目已有的账号、权限、模型配置、资产和任务体系。

两个项目的最终边界如下：

- `agent-tool` 负责从用户输入到 Remotion JSON 的完整内容生产流程。
- `remotion-video` 只负责校验 Remotion JSON、执行渲染并返回视频结果。
- PPT、PDF 等通用解析能力建设在 `agent-tool`，供轻量营销视频以及未来其他模块共同复用。
- 用户或系统配置的 AI API Key 只保存在 `agent-tool`，不下发给渲染服务。

这种拆分能够避免重复实现用户体系，也能防止 PPT/PDF 解析、AI 分析、图片生成和语音生成继续与 Remotion 渲染代码耦合。

## 2. 目标与非目标

### 2.1 目标

- 在 `/app/content/create_video?tool=lightweight-marketing-video` 提供完整的营销视频生产入口。
- 支持上传图片、视频、PPT、PPTX 和 PDF 作为参考附件。
- 复用统一的文档解析、素材存储、个人模型和系统模型配置。
- 分阶段生成内容分析、宣传图片、旁白、字幕和 Remotion JSON。
- 将最终 JSON 交给独立的 Node.js Remotion 服务渲染。
- 在 `agent-tool` 中统一持久化任务状态、生成产物、失败原因和操作记录。
- 为后续新增其他视频插件保留一致的插件注册和执行方式。

### 2.2 非目标

- 不允许通过管理页面动态上传并执行任意 Node.js 或 Go 代码。
- 不在 `remotion-video` 内增加用户、权限、积分、模型或 API Key 管理。
- 不让渲染服务直接调用 LLM、图片生成、TTS 或文档解析服务。
- 第一阶段不建设复杂的可视化时间线编辑器。
- 第一阶段不要求插件系统支持第三方不受信任代码。

## 3. 系统职责边界

| 能力 | `agent-tool` | `remotion-video` |
| --- | --- | --- |

| PPT/PDF/图片/视频解析 | 负责 | 不负责 |
| AI 内容分析 | 负责 | 不负责 |

```text
浏览器

  │ 上传、配置、查看进度
  ▼
agent-tool Go API
  ├── 用户 / 权限 / API Key / 积分
  ├── content_assets 素材与作品
  ├── 通用附件解析服务
  │     ├── PPT/PPTX
  │     ├── PDF
  │     ├── 图片元数据
  │     └── 视频元数据
  ├── 轻量营销视频工作流
  │     ├── AI 内容分析
  │     ├── 宣传图片生成
  │     ├── 旁白与字幕生成
  │     └── Remotion JSON 组装
  └── 渲染适配器
          │ 服务鉴权 + JSON
          ▼
     remotion-video Node.js
          ├── JsonVideo Schema 校验
          ├── Remotion 渲染队列

```

`agent-tool` 是业务事实来源。即使 Node.js 渲染进程重启，用户看到的任务、配置和历史记录也应由 `agent-tool` 持久化数据恢复。

## 5. 插件管理设计

### 5.1 插件的含义

这里的“插件”是 `agent-tool` 内受信任的业务能力注册，不是运行时上传任意代码的插件市场。

第一版建议采用代码注册加数据库配置：

- 代码定义插件标识、前端路由、输入能力、工作流阶段和结果类型。
- 数据库保存是否启用、显示顺序、渲染服务地址、超时、并发和模板版本等可变配置。
- 后端通过固定的插件接口调用工作流，不使用动态脚本执行。

### 5.2 轻量营销视频插件定义

建议插件标识保持为：

```text
lightweight-marketing-video
```

建议注册信息至少包含：

```json
{
  "key": "lightweight-marketing-video",
  "name": "轻量营销视频生成",
  "category": "video",
  "enabled": true,
  "requiredPermission": "web.module.content.create_video",
  "workflowVersion": "1",
  "renderAdapter": "remotion-json-video",
  "acceptedAttachments": ["image", "video", "ppt", "pptx", "pdf"]
}
```

管理端第一阶段只需要支持启用/停用、排序和渲染配置，不需要提供代码上传入口。

## 6. 业务工作流

### 6.1 用户流程

1. 上传参考附件。
2. 填写营销需求。
3. 解析附件并执行 AI 内容分析。
4. 根据分析结果生成和选择宣传图片。
5. 生成旁白、音频、字幕和场景时间轴。
6. 组装并校验 Remotion JSON。
7. 提交渲染服务。
8. 同步渲染进度并将完成视频保存到作品库。

### 6.2 建议任务状态

```text
draft
  → parsing
  → analyzing
  → generating_images
  → generating_narration
  → building_json
  → queued_for_render
  → rendering
  → completed
```

任一执行阶段都可以进入 `failed` 或 `cancelled`。重试应从失败阶段继续，已经成功且输入未变化的阶段不重复扣费或重复调用外部模型。

### 6.3 阶段输入输出

| 阶段 | 输入 | 输出 |
| --- | --- | --- |
| 附件解析 | 参考附件 | 文本、页面、图片、媒体元数据、解析警告 |
| AI 分析 | 营销需求、解析结果 | 摘要、卖点、受众、视觉方向、场景建议 |
| 宣传图片 | 分析结果、原始图片 | 生成图片资产、图片选择结果 |
| 旁白字幕 | 场景建议、文案、音色配置 | 音频资产、字幕片段、真实时长 |
| JSON 组装 | 场景、图片、音频、字幕 | 版本化的 `JsonVideo` 输入 |
| 视频渲染 | `JsonVideo` 输入 | 进度、MP4、错误信息 |

## 7. 通用附件解析

附件解析不应写在轻量营销视频插件内部，而应成为 `agent-tool` 的共享能力。

### 7.1 统一解析入口

建议以 `content_assets` 中的素材 ID 作为输入，异步生成解析记录。插件只引用解析结果，不直接读取用户上传的临时文件。

通用输出建议包含：

- 原始资产 ID、文件哈希、MIME 类型和解析器版本。
- 提取的全文和分页文本。
- 页码、幻灯片编号或视频时间范围等来源定位。
- 提取图片对应的新资产 ID。
- 图片宽高、视频时长、画面比例等媒体元数据。
- 解析状态、失败代码、警告和耗时。

### 7.2 文件类型策略

- `PPTX`：直接提取页面文本、备注和内嵌图片。
- `PPT`：先通过受控转换服务转为 PPTX 或 PDF，再进入统一解析流程。
- `PDF`：优先提取文本层；扫描件按需进入 OCR，并记录页码来源。
- 图片：读取尺寸、格式和必要的视觉分析信息，原文件继续由素材库管理。
- 视频：读取时长、宽高、帧率和封面；需要理解视频内容时再调用独立的视频分析能力。

### 7.3 复用与缓存

解析缓存键建议包含：

```text
文件内容哈希 + 解析器名称 + 解析器版本 + 关键参数
```

相同文件在不同插件中使用时可复用解析结果。解析结果必须保留用户和资产权限边界，不能因为命中缓存而泄露其他用户的原始文件信息。

### 7.4 第一阶段实现结构

通用解析内核位于 `backend/internal/assetextract`，采用静态注册的解析器接口，不把基础解析器做成可动态安装的业务插件：

- `Service`：根据规范化 MIME 类型和扩展名选择解析器。
- `PPTXParser`：使用 Go 标准库解析 Open XML 压缩包，输出幻灯片文本、内嵌图片、页面位置和图片分类信息。
- `PDFParser`：封装 Poppler 页面渲染，输出按页定位的派生图片；PDF 文本层提取和 OCR 属于后续能力。
- `ImageFilter`：PPTX 与 PDF 共用的版本化图片过滤规则，统一输出分类、是否纳入分析、置信度和过滤原因。文档整页参考图使用独立角色，避免被模板背景规则误删；未来 PDF 内嵌图片提取直接复用普通嵌入图片规则。
- `Result`：统一使用 `slide` 或 `page` 内容单元、派生文件、解析器名称、版本、警告和格式元数据表达结果。

现有 PDF 聊天参考图流程已经通过该统一入口调用，并继续将页面图片保存为 `content_assets`。在前端上传流程和 AI 分析调用切换到新的资产解析契约前，`remotion-video` 中旧的 PPTX 接口暂时保留兼容；完成调用迁移后再删除，最终渲染服务仍只接收 Remotion JSON。

资产解析后端契约已经提供：

- `POST /api/content/assets/{assetId}/extraction`：按资产 ID 异步触发解析，返回 `202` 和解析记录。
- `GET /api/content/assets/{assetId}/extraction`：读取该资产最新解析状态及结果。
- 已有相同解析器版本的成功结果时直接复用；`force=true` 可在没有运行中任务时重新解析。
- 解析记录存入 `asset_extractions`，状态为 `queued → running → completed/failed`。
- 内嵌图片和 PDF 页面保存为带 `parent_asset_id` 的派生 `content_assets`，解析结果只返回真实资产 ID，不保存 Base64 或本地文件路径。
- 图片过滤后仅将 `included=true` 的资源写入 `content_assets`；排除资源不落盘，解析结果只保存总数、保留数、排除数和分类统计。

解析记录生命周期规则：

- 每个资产最多保留 3 条终态记录，并始终保留最新成功结果。
- 失败记录默认保留 7 天，被新结果替代的成功记录默认保留 30 天。
- 超过 24 小时仍处于 `queued` 或 `running` 的任务标记为失败。
- 后台按临时素材清理设置中的间隔执行维护；服务启动时也会立即执行一次。
- 删除原始资产时，级联删除其解析记录和未被业务引用的派生资产，同时删除对应本地文件。

内容分析第一阶段已经接入 `content_planning_sessions`：

- 分析请求先写入 `analyzing/analyzing_materials` 状态，再由后台任务执行，前端通过会话查询轮询结果。
- 图片直接生成受限尺寸的视觉输入；PPTX 同时使用提取文本和过滤后的有效图片；PDF 使用解析后的页面图片。
- 模型必须通过 `submit_content_analysis` 工具返回结构化产品洞察、素材说明、参考结构和待确认事项，服务端会过滤模型返回的未知资产 ID。
- 分析结果写入策划会话的 `analysis`，不写入 `asset_extractions`；解析记录继续只负责确定性的文件内容提取。
- 使用现有默认或用户 LLM 配置，并按后台“内容策划分析”单次积分配置预扣、失败退回和成功结算。
- 当前视频与音频附件先保留为后续流程参考并明确标记未完成逐帧分析或转写；视频理解和音频转写在独立阶段补齐。

轻量营销视频页面在 AI 内容分析之前提供独立的“附件解析”阶段：上传 PPTX/PDF 后可显式触发解析，完成后通过按钮打开结果弹窗；弹窗按文档切换，左侧展示逐页文案，右侧展示过滤后写入 `content_assets` 的图片。没有文档附件时该阶段显示为无需执行，不阻塞普通图片和营销需求的 AI 分析。

AI 内容分析同时输出宣传图场景规划，包括全片统一视觉风格、2 至 6 个场景、场景文案、旁白、CTA、时长、图片提示词和真实参考素材 ID。宣传图片阶段通过 `POST /api/content-planning/sessions/:id/campaign-images` 异步按场景生成 16:9 图片；结果保存到 `content_assets`，策划会话仅保存生成状态、场景关联和资产 ID。页面刷新后通过策划会话恢复进度和结果，不依赖浏览器内存。

## 8. 数据与任务建议

优先复用现有 `content_assets`、用户模型配置、视频作品和积分能力。新增数据可以围绕以下概念设计，实际表名在实现阶段结合现有 Store 规范确定：

- `plugin_definitions`：插件标识、名称、版本和能力声明。
- `plugin_settings`：启用状态、排序和非敏感运行配置。
- `marketing_video_tasks`：用户任务、营销需求、当前阶段、版本和错误。
- `marketing_video_task_assets`：任务输入、生成图片、音频、字幕和视频等资产关联。
- `asset_extractions`：通用附件解析状态、版本和结构化结果。
- `render_jobs`：`agent-tool` 主任务与 Node.js 渲染任务 ID 的映射。

大文本分析结果和 Remotion JSON 可以使用 JSON 字段持久化，但关键查询字段，如状态、用户 ID、阶段、版本和时间，应保留独立列。

每个阶段记录输入摘要或版本号。用户修改营销需求、替换图片或重新生成旁白时，根据依赖关系将下游阶段标记为过期。

## 9. Remotion JSON 与渲染契约

### 9.1 当前可复用契约

`remotion-video` 当前已经提供以下接口：

- `POST /renders`：提交 `{ compositionId: "JsonVideo", inputProps }`。
- `GET /renders/:jobId`：查询状态和进度。
- `DELETE /renders/:jobId`：取消排队中或渲染中的任务。
- `GET /renders/:jobId/video`：读取完成后的 MP4。

当前 `inputProps` 使用 `version: "1.1"` 的 JsonVideo 数据，包含 `video`、`scenes`、`elements`、动画和转场等字段。接入时应复用 `src/JsonVideo/schema` 的 Schema，而不是在两个项目里分别手写不一致的校验规则。

### 9.2 建议补强

生产接入前建议为渲染接口增加：

- 服务间鉴权，不暴露为匿名公网接口。
- `requestId` 或幂等键，避免网络重试创建重复渲染。
- 请求体大小、场景数、总帧数和素材数量限制。
- 模板和 JSON Schema 版本协商。
- 结构化错误码，而不是只返回错误字符串。
- 渲染超时、并发限制和磁盘空间保护。
- 结果下载有效期或由 `agent-tool` 主动拉取并落入素材库。

`remotion-video` 当前任务队列保存在内存中，进程重启后任务会丢失。第一版可以由 `agent-tool` 持久化主任务并识别渲染任务失联；正式运行时应进一步选择持久化 Node.js 队列，或让 `agent-tool` 在明确的幂等规则下重新提交。

### 9.3 素材访问

Remotion JSON 中不要出现服务器本地绝对路径。推荐使用以下方式之一：

1. `agent-tool` 生成短期签名素材 URL，由渲染服务在任务有效期内读取。
2. 提交渲染前由适配器将所需素材复制到渲染任务目录，再把 JSON 中的地址改为任务内资源地址。

无论采用哪种方式，都应限制允许访问的协议、域名、文件大小和超时时间，避免利用渲染器访问内网任意地址。

## 10. 前端规划

当前 `/app/content/create_video` 已新增“轻量营销视频生成”，并默认选中该工具。页面已先完成以下前端结构：

- 参考附件：复用 `video-task-material-slot`，支持图片、视频、PPT、PPTX 和 PDF。
- 营销需求：简洁的多行文本输入。
- AI 内容分析。
- 宣传图片。
- 旁白与字幕。
- Remotion JSON。
- 视频渲染。

后端接入时建议每个阶段显示 `未开始 / 处理中 / 已完成 / 失败 / 已过期`，并允许查看阶段产物和针对单个阶段重试。页面不应把整个流程压缩为一次不可恢复的长请求。

附件上传后应立即创建素材资产并显示解析状态。PPT/PDF 解析、AI 分析、图片生成和渲染均应使用异步任务，不阻塞普通 HTTP 请求。

### 通用工作流状态持久化

口播视频、营销视频和轻量营销视频统一使用 `content_workflows` 保存页面恢复所需的编排状态。该表以 `user_id + module_key + record_key` 唯一定位记录：没有列表的编辑草稿使用 `record_key=default`，有列表的任务使用业务任务 ID。

`state` JSON 只保存版本化的模块状态、素材 ID、当前步骤和业务任务关联 ID，不保存文件二进制，也不复制解析结果、AI 结果、分镜或视频任务数据。具体产物继续分别以 `content_assets`、`asset_extractions`、`content_planning_sessions`、营销分镜表和视频任务表作为真实来源。

三个模块当前约定：

- `talking-video`：保存输入草稿，并关联口播提示词任务 ID 和视频任务 ID。
- `marketing-video`：保存产品信息、补充要求、素材草稿，并关联分镜任务 ID和视频任务 ID。
- `lightweight-marketing-video`：每条创作记录保存附件资产 ID、营销需求、解析步骤和 AI 策划会话 ID。

本地 `File` 和 `blob:` URL 不可持久化。需要跨刷新恢复的素材必须先上传为 `content_assets`，恢复时再根据资产 ID 重新构造前端素材对象。

## 11. 权限、API Key 与计费

- 页面和接口沿用 `web.module.content.create_video` 权限。
- 所有输入资产、阶段产物和最终视频都校验当前用户所有权。
- 个人模型优先级继续沿用 `agent-tool` 已有用户模型配置规则。
- API Key 只在 Go 后端调用外部服务时解密使用，不写入任务 JSON、日志或 Remotion JSON。
- 每个外部模型阶段独立记录调用和费用，渲染费用与 AI、图片、TTS 费用分开核算。
- 阶段失败只结算已经实际完成的调用；重试必须具备防止重复计费的幂等标识。
- 管理端只能查看配置是否完成，不能回显完整密钥。

## 12. 分阶段实施

### 阶段 0：前端骨架

- 新增轻量营销视频工具和默认路由。
- 完成参考附件、营销需求和各工作流阶段的精简界面。
- 未接入的动作保持明确禁用状态。

### 阶段 1：插件注册与任务骨架

- 增加受信任插件注册表和启用配置。
- 增加营销视频主任务及阶段状态持久化。
- 前端能够创建草稿、恢复任务和查看状态。

### 阶段 2：附件上传与通用解析

- 复用素材库上传和权限模型。
- 实现 PPTX、PDF、图片和视频解析。
- 明确旧版 PPT 的转换策略。
- 建立解析缓存、错误码和解析结果查看能力。

### 阶段 3：AI 分析与宣传图片

- 接入个人或系统 LLM。
- 固化内容分析的结构化 Schema。
- 接入图片模型，并将结果保存为 `content_assets`。
- 支持选择、重新生成和下游失效处理。

### 阶段 4：旁白、字幕与 JSON

- 接入 TTS 音色、语速和试听。
- 依据真实音频时长生成字幕及场景时间轴。
- 在 Go 侧生成版本化 JsonVideo 输入并完成预校验。
- 支持查看 JSON 和必要的高级编辑，但默认不要求用户手写 JSON。

### 阶段 5：Remotion 渲染接入

- 增加服务间鉴权和渲染适配器。
- 完成提交、进度同步、取消、超时和重试。
- 将 MP4 拉取到 `agent-tool` 文件存储并创建作品记录。
- 增加幂等、任务恢复和异常进程处理。

### 阶段 6：运维与扩展

- 增加并发、队列长度、失败率、渲染耗时和磁盘监控。
- 完成阶段级计费与审计。
- 抽取可复用的插件工作流接口，用于接入其他 JSON 视频模板。

## 13. 验收标准

- 同一账号能够创建、离开并恢复轻量营销视频任务。
- 图片、视频、PPT/PPTX 和 PDF 均能上传并得到明确的解析状态。
- PPT/PDF 解析结果可以被其他业务模块复用。
- AI 分析、图片、旁白、字幕和 JSON 都有可追踪的阶段产物。
- 修改上游输入会准确使相关下游结果过期。
- `remotion-video` 在没有任何用户 API Key 的情况下，仅凭合法 JsonVideo 输入完成渲染。
- Node.js 渲染失败或重启不会导致 `agent-tool` 主任务和历史记录丢失。
- 最终 MP4 保存为当前用户的作品，不能被其他用户越权访问。
- 日志、错误响应、任务上下文和 Remotion JSON 中不包含明文 API Key。

## 14. 实施前需确认的问题

- 旧版 `.ppt` 采用 LibreOffice 转换、独立转换服务，还是第一版只上传并提示暂不解析。
- Node.js 渲染服务采用持久化队列，还是由 `agent-tool` 统一持久化并通过幂等请求恢复。
- 渲染素材采用短期签名 URL，还是复制到隔离的渲染任务目录。
- JsonVideo Schema 由独立包共享，还是在发布流程中从 `remotion-video` 导出版本化 JSON Schema。
- TTS 首批支持的提供方、音色范围和计费方式。
- 工作流是否允许用户编辑最终 JSON，以及编辑后如何标记 AI 阶段产物和支持责任边界。

以上问题不影响前端骨架和通用附件解析先行，但应在开始渲染服务正式接入前确定。
